# VIQ Upgrade — Stage 2a: Backend Pagination & Query Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give every list-returning endpoint that currently fetches its whole table (`GET /trips`, `/services`, `/persons`, `/audit`) an opt-in pagination mode, add the four missing indexes those queries actually need, batch the audit log's per-field write pattern into one statement, and configure an explicit database connection pool size — all four the direct causes behind the VIQ Scale Review's "nothing paginates" cross-cutting finding and its concrete, live evidence (the Audit Trail's 387-row unpaginated render, already near its old 1,000-row cap).

**Architecture:** Backend-only. Every endpoint's pagination is **strictly additive and opt-in**: when a caller doesn't pass `page`, the endpoint returns exactly what it returns today (a plain array) — zero risk to any existing frontend code, since nothing in the current frontend passes `page`. When `page` is passed, the endpoint switches to returning `{ data, page, limit, total, totalPages }`. This deliberately splits the work: this plan lands the backend capability with no frontend change; a separate follow-up plan (Stage 2b, not this one) rewires the frontend to actually request paginated data and adds the search/scroll UI — including a real fix for `TripsPage.tsx`'s current N-way-parallel-fetch-per-trip pattern, which is its own architectural problem beyond pagination and deserves its own focused plan.

**Tech Stack:** NestJS 10 / Prisma 5 / PostgreSQL 16. No new dependencies.

**Spec:** None. Resolved via the ChatGPT peer-review debate and the pagination-contract design confirmed with the user before this plan was written (offset-based `?page=&limit=`, not cursor-based — VIQ's current data volume doesn't justify cursor pagination's added complexity; that call can be revisited if offset-scan cost is ever actually measured as a problem).

### Task 2: Batch `AuditService.logDiff()`'s per-field writes

**Files:**
- Modify: `src/server/modules/audit/audit.service.ts`

**Interfaces:**
- Produces: `AuditService.logDiff(user, table, recordId, before, after): Promise<void>` — same signature as today, every existing caller across the app (Trips/Legs/Services/Persons/Docs/Invoices) is unaffected.

**Why this matters:** `logDiff()` currently does one `await this.log(...)` per changed field, sequentially, inside a `for` loop — a real N+1 on writes. A 6-field trip update does 6 sequential round-trips to Postgres just for audit logging, on every edit, app-wide.

- [ ] **Step 1: Replace the loop with one batched insert**

Find:

```ts
  // Diffs two flat records and logs one entry per changed field.
  async logDiff(user: string, table: string, recordId: string, before: Record<string, unknown> | null, after: Record<string, unknown>) {
    if (!before) {
      await this.log(user, table, recordId, 'Created', '', recordId);
      return;
    }
    const keys = new Set([...Object.keys(before), ...Object.keys(after)]);
    for (const key of keys) {
      const oldVal = before[key];
      const newVal = after[key];
      const oldStr = oldVal === undefined || oldVal === null ? '' : String(oldVal);
      const newStr = newVal === undefined || newVal === null ? '' : String(newVal);
      if (oldStr !== newStr) {
        await this.log(user, table, recordId, key, oldStr, newStr);
      }
    }
  }
```

Replace with:

```ts
  // Diffs two flat records and logs one entry per changed field, batched
  // into a single INSERT rather than one sequential round-trip per field.
  async logDiff(user: string, table: string, recordId: string, before: Record<string, unknown> | null, after: Record<string, unknown>) {
    if (!before) {
      await this.log(user, table, recordId, 'Created', '', recordId);
      return;
    }
    const keys = new Set([...Object.keys(before), ...Object.keys(after)]);
    const changes: { user: string; table: string; recordId: string; field: string; oldValue: string; newValue: string }[] = [];
    for (const key of keys) {
      const oldVal = before[key];
      const newVal = after[key];
      const oldStr = oldVal === undefined || oldVal === null ? '' : String(oldVal);
      const newStr = newVal === undefined || newVal === null ? '' : String(newVal);
      if (oldStr !== newStr) {
        changes.push({ user, table, recordId, field: key, oldValue: oldStr, newValue: newStr });
      }
    }
    if (changes.length === 0) return;
    await this.prisma.auditEntry.createMany({ data: changes });
  }
```

### Task 3: Add opt-in pagination to `GET /trips`

**Files:**
- Modify: `src/server/modules/trips/trips.controller.ts`
- Modify: `src/server/modules/trips/trips.service.ts`

**Interfaces:**
- Produces: `TripsService.findAllPaginated(page: number, limit: number): Promise<{ data: Trip[], page: number, limit: number, total: number, totalPages: number }>` — new method, additive. `TripsService.findAll()` (no args) is completely unchanged.
- Consumes: nothing from earlier tasks (independent of Tasks 1-2, though benefits from Task 1's `Trip.createdZ` index once both have landed).

**Contract:** `GET /trips` with no `page` query param returns exactly what it returns today — a plain `Trip[]` array, sorted by `createdZ` descending. `GET /trips?page=1&limit=50` returns the envelope shape instead. Default `limit` when `page` is passed but `limit` isn't: 50. Maximum `limit`: 200 (a request for more is silently clamped, not rejected).

- [ ] **Step 1: Add the paginated service method**

In `src/server/modules/trips/trips.service.ts`, find:

```ts
  findAll() {
    return this.prisma.trip.findMany({ orderBy: { createdZ: 'desc' } });
  }
```

Replace with:

```ts
  findAll() {
    return this.prisma.trip.findMany({ orderBy: { createdZ: 'desc' } });
  }

  async findAllPaginated(page: number, limit: number) {
    const skip = (page - 1) * limit;
    const [data, total] = await Promise.all([
      this.prisma.trip.findMany({ orderBy: { createdZ: 'desc' }, skip, take: limit }),
      this.prisma.trip.count(),
    ]);
    return { data, page, limit, total, totalPages: Math.ceil(total / limit) };
  }
```

- [ ] **Step 2: Route to it when `page` is present**

In `src/server/modules/trips/trips.controller.ts`, find:

```ts

  }
```

Replace with:

```ts
  @Get()
  findAll(@Query('page') page?: string, @Query('limit') limit?: string) {
    if (page === undefined) {
      return this.trips.findAll();
    }
    const pageNum = Math.max(1, Number(page) || 1);
    const limitNum = Math.min(200, Math.max(1, Number(limit) || 50));
    return this.trips.findAllPaginated(pageNum, limitNum);
```

### Task 7: Configure an explicit Prisma connection pool limit

**Files:**
- Modify: `.env.example`

**Interfaces:** None.

**Why this matters:** Prisma's unconfigured default connection pool size is `num_physical_cpus × 2 + 1` *per process*. With no explicit limit, running VIQ as multiple instances later would each open their own default-sized pool against the one Postgres instance, risking exhausting Postgres's own `max_connections` (100 by default) well before a realistic instance count. This task documents an explicit, safe default; it does not itself introduce multi-instance deployment or PgBouncer — those are real infrastructure decisions to make once there's an actual multi-instance target to size against, not something to bolt on speculatively here.

- [ ] **Step 1: Add the connection limit to the example**

In `.env.example`, find:

```
DATABASE_URL="postgresql://jetflow:jetflow@localhost:5442/jetflow?schema=public"
```

Replace with:

```
# connection_limit is explicit rather than left to Prisma's default
# (num_physical_cpus * 2 + 1 per process) — that default doesn't account
# for multiple server instances sharing one Postgres, and could exhaust
# Postgres's own max_connections (100 by default) well before a realistic
# instance count. 10 is a reasonable single-instance default; if/when VIQ
# runs as N instances, size this so N * connection_limit stays safely below
# Postgres's max_connections, or introduce PgBouncer in front of Postgres.
DATABASE_URL="postgresql://jetflow:jetflow@localhost:5442/jetflow?schema=public&connection_limit=10"
```

- [ ] **Step 2: Add the same parameter to your own local `.env`**

```bash
node -e "
const fs = require('fs');
let c = fs.readFileSync('.env', 'utf8');
if (!c.includes('connection_limit')) {
  c = c.replace(
    /DATABASE_URL=\"([^\"]+)\"/,
    (match, url) => 'DATABASE_URL=\"' + url + (url.includes('?') ? '&' : '?') + 'connection_limit=10\"'
  );
  fs.writeFileSync('.env', c);
  console.log('Updated .env');
} else {
  console.log('.env already has connection_limit, left unchanged');
}
"
cat .env | grep DATABASE_URL
```
