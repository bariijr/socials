VIQ Scale Review

A full-system review of VIQ — security re-scan, live visual walkthrough, architecture & data-management analysis, and a scalability assessment — targeting one specific goal: this single-tenant internal aviation trip-support tool serving thousands of concurrent users across many internal divisions of one organization (not a multi-tenant product; one shared instance, far more usage).

What VIQ is, for a reader with no prior context: an internal aviation trip-operations tool — NestJS 10 + Prisma 5 + PostgreSQL 16 on the server, React 19 + Vite on the client, one unified source tree. It manages trips, legs, overflight/landing permits, ground handling, crew & passenger rosters, documents (with OCR), billing, and vendor/CAA communications for a flight-support/permits desk. Today it runs as a single process for a single admin's local testing. This document evaluates what changes — technically and functionally — between that today and the stated scale target.

Executive summary

VIQ's Phase 1-3 hardening pass (11 tasks, completed 2026-08-27) is confirmed fully and correctly landed — 7/7 claimed fixes verified directly against live source and, where practical, live HTTP behavior. Nothing in this review found a regression from that work. What this review adds is a second layer: three findings were independently discovered by two or more of the four specialist reviews run for this document, which is the strongest signal in this whole report — when a security reviewer, an architecture reviewer, and a scalability reviewer each read the code cold and land on the same conclusion, that conclusion deserves to be first in line, not buried among sixty other observations.

Those three are: (1) the rate limiter just added in Phase 1-3 uses in-memory storage that silently stops working the moment VIQ runs as more than one process — the fix is well understood (Redis-backed storage) but must happen before, not after, horizontal scaling begins; (2) no endpoint in the app paginates, and the audit trail's live 387-row unpaginated render plus its hard 1,000-row cap is concrete proof this pattern is already at its ceiling, not a future risk; (3) a real, already-diagnosed trip-ID race condition gets mechanically worse — not just "still present" — as concurrent usage grows.

Beyond the technical review, the user's own stated product vision (landing-page lead capture → coordinator actioning with email notification → periodic client status emails → consolidated multi-trip billing → admin-maintained client/reference data) was checked directly against the codebase. Four of its five pillars are not yet built — not partially built, not stubbed, genuinely absent: there is no Client entity (a trip's client is a free-text string), no scheduled-job infrastructure exists anywhere in the project, no email fires when a public quote is submitted, and invoice generation only ever handles one trip at a time. Section 8 treats this as its own first-class finding, since it changes the shape of "what's next" more than any individual bug fix does.

Nothing in this review reaches Critical. The pentest re-scan's one new practically-exploitable item (unthrottled login) is fixable in an afternoon using a pattern already proven elsewhere in this same codebase.

00

Cross-cutting findings

Found independently by 2 or more of the four specialist reviews (security, scalability, architecture/data, UX) without being told to look for each other's conclusions. Independent convergence is the strongest confidence signal this report can offer a peer reviewer — read these three first.

Confirmed by 3 reviewsThe Phase 1-3 rate limiter silently weakens under horizontal scaling
quotes.module.ts:10 — ThrottlerModule.forRoot([{ ttl: 60000, limit: 5 }]), no storage: option

@nestjs/throttler's default storage is an in-memory Map, scoped to one Node process. Today, with exactly one process, the 5-req/min/IP limit on /api/quotes works exactly as intended. The moment VIQ runs as N instances behind a load balancer — the natural shape of "1,000s of concurrent users" — each instance tracks its own counter. A client load-balanced across N instances can send up to 5×N requests/minute before any single instance returns 429. No error, no warning, no test would catch this without specifically checking for it.

Why three separate reviews found this independently: the security re-scan flagged it as a control that "stops doing what it says," the scalability review flagged it as a statelessness violation, and the architecture review flagged it as the same in-memory-cache-per-process shape as the (harmless) client-side reference-data cache — three different lenses on the identical root cause.

Fix — swap the default storage for a Redis-backed ThrottlerStorage implementation before introducing a second instance. Small effort once Redis exists; do this and the login-throttle fix (Section 2, F1) together, since both want the same shared store.

Confirmed by 4 reviews, with live evidenceNothing paginates — and it's already visibly at its ceiling today
GET /trips, /services, /persons, /audit all findMany() with no skip/take/cursor

Every list-returning endpoint fetches its entire result set every time. This was flagged by the security review (unbounded ?limit=), the scalability review (payload size, query cost), the architecture review (compounds directly with missing indexes), and the UX/visual review — which is the one that turned this from a theoretical risk into observed fact: the live Audit Trail page rendered 387 rows into the DOM in one response, and the endpoint's own hard cap of 1,000 rows means history beyond that becomes silently unreachable through the UI, not gracefully paginated.

Even a perfectly-indexed unbounded query is still an unbounded query. At "many divisions" scale this is the dominant future cost driver in the whole system — more so than any single missing index.

Fix — additive ?page=/?limit= or cursor params on every list endpoint, defaulting to today's behavior so nothing breaks immediately; land incrementally, starting with Audit (closest to its cap today). Medium effort, real but mechanical backend+frontend work — not a rewrite.

Confirmed by 2 reviews (Phase 1-3 + scalability), gets mechanically worse at scalenextTripId()'s race condition is a scale-blocking correctness bug, not a nice-to-have
src/server/modules/trips/trips.service.ts:15-20 — count() then format(count+1), no lock, no retry

Already diagnosed during Phase 1-3's own rate-limiter testing (5 rapid public quote submissions reliably reproduced it — two requests read the same count, collide on the ID's unique constraint, and the second 500s). The scalability review's contribution here: this isn't just "still present," it gets combinatorially more likely as concurrent submissions rise, and a naive single-process retry loop doesn't fully solve it once there are multiple processes racing over the same database value — the fix needs to be correct under concurrent processes, not just concurrent requests.

Fix — generate the ID inside the transaction with a retry-on-conflict loop, or replace count-then-format with a real Postgres sequence. Whichever is chosen, verify it under concurrent processes explicitly, not just concurrent requests to one process.

New findings unique to this pass

F1 — POST /auth/login has zero rate limiting

The only endpoint that issues credentials is completely unthrottled — a classic brute-force/credential-stuffing surface, exploitable today, at any scale, and more attractive as the user base (and thus weak/reused-password odds) grows.

Fix — apply the exact same @nestjs/throttler pattern already proven on /api/quotes, e.g. 5-10 attempts/min/IP, ideally paired with a per-username counter for defense in depth.

F3 — The CORS fix's safety depends on an undocumented env var

Task 6's production-safe CORS default only activates when NODE_ENV=production is actually set — and .env.example, the file an operator is most likely to copy, has no NODE_ENV line at all. A real deployment that copies the example and fills in secrets silently keeps the permissive pre-fix behavior.

Fix — add NODE_ENV=production to a production-specific env example, and/or log a loud startup warning when it's ambiguous.

F4 — No helmet/security response headers

Defense-in-depth, not a live hole (the magic-byte check already closes the main MIME-confusion vector). npm install helmet and app.use(helmet()) — verify its CSP defaults don't fight the SPA's own inline styles before enabling CSP specifically; the other headers are safe unconditionally.

F5 — Stale .env.example references a removed auth mechanism

ADMIN_USERNAME/ADMIN_PASSWORD_HASH are seed-time-only now (per README), but .env.example still implies they're live config. Documentation gap, not a vulnerability.

Already solid — confirmed unchanged by this re-scan
  • Password hashing, JWT-secret fail-closed behavior, correct guard ordering, zero SQL injection surface, secrets hygiene, path-traversal-proof uploads — all re-spot-checked, no regressions from Phase 1-3.
  • RBAC on Trips/Persons/Legs/Services/Stops/Comms/PersonRatings remains intentionally open to any Coordinator — a stated, unchanged design decision (see the priority matrix's UX3 for the related "should divisions be scoped" open question, which is explicitly a policy call, not a security gap).

Simplification (no functionality change)

Full report: .superpowers/audit-2026-08-27-architecture-data.md. Every item below is a pure refactor — same behavior, same routes, same schema.

SP1 — dataStore.ts is 1,869 lines covering ~20 unrelated resource types

Trip/Leg/Service CRUD, roster/ratings, comms, docs/OCR, audit, invoices+PDF/QR, and all 9 reference-data resources' shared cache — one file, 100+ exported functions.

Fix — split into per-domain modules under src/client/lib/data/ (trips, persons, docs, comms, invoices, reference, audit, format), with dataStore.ts becoming a barrel (export * from './data/trips', etc.) — every existing import keeps working unchanged. Medium effort, low risk; tsc catches any missed reference immediately.

SP2 — TripDetail.tsx bundles 11 already-separable components in one 2,008-line file

LegEditor alone (~600 lines) is bigger than most other page files in the app. Each sub-component already has a clean, self-contained props interface — this is unmoved code, not tangled state.

Fix — extract each to its own file under src/client/components/trip-detail/, one at a time with a build+smoke-test after each, given this is the app's highest-traffic page.

SP-U1 — The urgency predicate is duplicated 4 times, plus a third independent rank encoding

Urgency === 'URGENT' || Urgency === 'BREACH' appears independently in Dashboard.tsx, AdminDashboard.tsx (twice), and Layout.tsx; AdminTrips.tsx separately reimplements the same four-value severity order that dataStore.ts's urgencyRank() already provides. This already caused the real, live 33-vs-34 discrepancy documented in Section 0 — not hypothetical drift, observed drift.

Fix — one exported isUrgentOrBreach() helper, all four call sites use it; replace AdminTrips.tsx's local rank table with the existing urgencyRank() export. Under an hour, very low risk.

SP3 — One confirmed dead dependency

@types/content-disposition@^0.5.9 describes an API shape the code doesn't even use (TypeScript resolves the real package's own bundled types instead). Safe to npm uninstall. Already flagged as a deferred minor in the Phase 1-3 ledger.

Already good — no drift found
  • The reference-data cache-at-boot pattern (getXList()/saveX/preloadReferenceData()) is applied consistently across all 9 resources it covers — no resource reinvents its own fetch-and-cache shape.
  • The Reference-Data-vs-Admin-Assets duplication (Airports/Countries manageable from two pages) remains open but is already this project's own tracked Phase 4 — not re-investigated here.
05

UI/UX & flow upgrades

Full report: .superpowers/audit-2026-08-27-ux-flow.md. Each proposal states what/why-at-this-scale/effort/what it explicitly does NOT require — this is an upgrade path, not a rebuild. Vision-driven proposals (email/notification UX) are cross-referenced to Section 8.

UX1 — A passive "someone else already touched this" signal on Trip Detail

A "Last updated by {user} at {time}" banner sourced from the trip's own most recent audit entry — data that already exists. At today's scale, checking the Activity tab is a reasonable ask; at many-divisions scale, the odds of two people acting on the same shared trip within minutes rise sharply and there's currently zero passive signal.

Does not require: a notification system, WebSockets, or any Audit/Comm data-model change. One read, one banner.

UX2 — Bulk actions on the New Enquiries queue

Checkbox-select + batch "Assign to me"/"Mark reviewed", reusing the exact pattern already proven twice elsewhere in this codebase (service-card multi-select, country-permit batch submission). Today's one-at-a-time triage is fine at today's volume; it becomes the bottleneck at many-divisions volume even though no individual action is slow.

UX3 — An optional division tag and default-scoped Trips view — a policy question, not a recommendation

Today, RBAC is flat: any Coordinator can see/act on any trip — a documented, deliberate choice at today's scale. Whether that's still the right default view (not permission model) once many divisions share one instance is genuinely a question for the organization, not something to assume. Proposed as view-scoping only — permissions stay exactly as they are — so if the answer is "no, shared visibility is exactly what we want," this costs nothing to skip.

Does not require: multi-tenancy, per-division databases, or any RBAC change — unless the follow-up decision is to add real access restriction, which would be its own design pass.

What's already good and shouldn't change
  • The leg-scoped Crew & Pax manifest, the unified generateEmail() template system, the country-permit batch-submission grouping, and the New Enquiries filter are all patterns that already scale well in design — several proposals above (UX1, UX2) deliberately reuse them rather than inventing new ones.
  • Mobile/field readiness: the sidebar's responsive shrink-to-hamburger pattern is a reasonable stopgap; this project's already-agreed Phase 6 (PWA + bottom-nav) is the correct planned answer — not a new gap to add here.
06

Data management logic

Full report: .superpowers/audit-2026-08-27-architecture-data.md. The Client-entity and consolidated-billing gaps below are new, surfaced by checking the user's stated product vision (Section 8) against the schema — not part of either fork's original brief.

D1 — Trip has zero indexes beyond its primary key; Service.urgency and AuditEntry.timestampZ are unindexed hot-path columns

GET /trips does findMany({ orderBy: { createdZ: 'desc' } }) with no WHERE, no LIMIT, no index — a full table scan on every page load, called by two different pages. Every dashboard load pulls every service row ever created to filter for urgency client-side. The audit table — the fastest-growing table in the schema — has no index on its own most common access pattern (recent-first).

model Trip { @@index([status]) @@index([createdZ]) } model Service { @@index([urgency]) } model AuditEntry { @@index([timestampZ]) }

Fix — one additive Prisma migration. Zero application-code change required alongside it — same queries, faster.

D2 — AuditService.logDiff() is an N+1 on writes: one sequential INSERT per changed field, on every mutation, app-wide

A trip update touching 6 fields does 6 sequential audit-log round-trips on top of the actual update. Every mutating endpoint in the app goes through this one function, so fixing it once fixes it everywhere.

Not a correctness bug — audit entries are accurate — but at high concurrent write volume this multiplies database round-trips for the single most common operation type, and each held connection feeds back into the connection-pool pressure covered in Section 7.

Fix — batch into one createMany call instead of N sequential create calls. Self-contained, no schema change.

D3 — Service-generation loops do sequential, unbatched (but correctly idempotent) writes per country

generateOverflightServices/generateArrivalServices do 3 sequential lookups + create + audit-log per country a leg overflies — not a correctness bug (deterministic IDs, idempotent, resumable exactly as documented), but slower than necessary and holds a pooled connection open longer than the work requires.

Fix, optional — batch the independent lookups with Promise.all per country; only worth doing if measured as a real bottleneck under load. Lower priority than the read-path fixes above (D1, D2), since this runs once per leg save, not on every page load.

D5 — @MaxLength discipline stops at the public endpoint

Phase 1-3 added size caps to the public CreateQuoteDto after an audit flagged it; spot-checking the authenticated CreateTripDto shows the identical gap on client/notes/operationType/etc. Lower severity (requires a valid JWT), but the same class of issue, unaddressed everywhere an audit didn't happen to look.

V1 — No first-class Client entity exists (surfaced via the vision-gap check, Section 8)

Trip.client is a plain, unconstrained String — not a foreign key to any client record. There is nowhere to store a client's contact info, billing address, or (per the user's stated vision) a per-client notification-interval preference, and no reliable way to group "every trip for this client" for consolidated billing beyond fuzzy-matching a free-text field.

This single gap is what actually blocks three of the user's five stated workflow pillars (B's client-copy email needs a client contact; C's per-client interval needs a client profile to hang the setting on; D's consolidated billing needs a reliable client grouping key) — it's the highest-leverage single addition in this entire document relative to the stated product vision.

Recommended path — add a Client model (contact info, billing address, notification-interval preference), add Trip.clientId as a nullable foreign key alongside the existing free-text field during migration (don't force a breaking backfill), and build Client CRUD in Reference Data/Admin Assets the same way Operator/Provider already work. Deliberately kept separate from Operator — per the user's own framing, a client commercially engages VIQ's services and may or may not be the aircraft's operator.

07

Scalability review

Full report: .superpowers/audit-2026-08-27-scalability.md. Static analysis only — no load test was run (no tooling in this project supports one yet); confidence levels are noted per finding.

S1 — Connection-pool math doesn't survive a second instance

No explicit connection_limit anywhere; Prisma's unconfigured default is num_physical_cpus × 2 + 1 per instance. A plausible fleet (e.g. 12 instances × 4 vCPUs → up to 108 connections) already exceeds Postgres 16's default 100-connection ceiling before counting anything else. This fails hard, not gracefully — Postgres rejects new connections outright, surfacing as random 500s under load.

Fix — set connection_limit explicitly in DATABASE_URL sized so instances × limit < max_connections, and/or put PgBouncer in front of Postgres — the standard pattern for many-instances-one-database.

Confirmed correctly stateless otherwise

TripsService.sheet() — the app's heaviest read — uses nested includes correctly, single round-trip, not N+1. PersonsService's joins are likewise correct. The OCR worker and mail transporter hold per-instance state, but it's compute capacity, not shared correctness-critical state — no problem at multi-instance scale (OCR throughput is a separate, lower-priority concern, see below). JWT auth is fully stateless by design — the right shape for horizontal scaling.

B1 — No frontend code-splitting: one 1.3MB chunk shipped to every visitor regardless of role

App.tsx eagerly imports every page including every admin-only one a typical Coordinator never visits. react-router's route table is already the natural split boundary.

Fix — convert admin-page imports to React.lazy() + a Suspense boundary. Low effort, no other build config change needed for a first pass.

No health endpoint, no structured logging

Zero routes resembling a health check anywhere — a load balancer has nothing to poll to know an instance should stop receiving traffic. Logging is Nest's default human-text console output — fine for one person watching a terminal, not for correlating incidents across a fleet.

Minimal first step — one GET /api/health route doing a trivial DB round-trip, returning 200/503 — tiny effort, unblocks correct load-balancer behavior. Defer full structured logging until multi-instance infra actually exists (Nest's LoggerService interface swaps to Pino later without touching call sites — no rework risk in waiting).

Session/auth design gets concretely worse at higher headcount — not hypothetically

12h stateless JWTs, no revocation, deactivation only checked at login. At one admin and a few coordinators, "wait up to 12h" is a rare tolerable edge case. Across many divisions with hundreds-to-thousands of accounts, the base rate of "someone needs cutting off now" (offboarding, lost device, leaked credential) rises with headcount, with currently no way to do it.

Fix — short-lived access token (~15min) + refresh token checked against a small revocation store (a Redis set, or a revokedAt check on refresh) — bounds the exposure window without abandoning stateless request-path auth. Real, non-trivial follow-up project; sequence after the Redis infrastructure above since it benefits from the same store.

OCR's single Tesseract worker is a per-instance throughput ceiling, not a correctness issue

Concurrent OCR requests to the same instance queue behind each other. Invisible today (occasional, user-initiated); worth a small worker pool or a background job queue only if measured as a real bottleneck under actual document-heavy load — don't build ahead of evidence.

Product vision vs. current implementation

The user's own stated end-to-end workflow vision, checked directly against the codebase rather than assumed. Four of five pillars are genuinely unbuilt today — this section exists because it changes the shape of "what's next" more than any individual bug fix in this document.

APublic landing page as a lead-magnet/CTA for trip & adhoc-permit submissions

Today

Built and working — LandingHero.tsx's Charter/Permit-only chooser, feeding the existing quote form and POST /api/quotes. Rate-limited and size-capped as of Phase 1-3.

Gap

None functionally — this pillar is already built. The UX report's UX1-UX3 proposals are the relevant polish layer, not a gap.

BSubmission goes live for coordinator/admin actioning, with an email notification to admin/coordinator + a copy to the client

Today

The "goes live for actioning" half exists (the New Enquiries filter + nav badge, built earlier this session). The email half does not exist — confirmed by direct inspection: QuotesService has zero mail-sending code, no import of MailModule anywhere near the quotes path.

Gap → V2

Wire QuotesModule to the already-working MailModule/Nodemailer (proven elsewhere for Comms's Send & Log flow) — fire one email to a configurable admin/coordinator address plus one to dto.contactEmail on successful submission. Low-Medium effort: the mail infrastructure already exists and works, this is new call sites and two templates, not new plumbing.

CAutomatic client status-update emails every XX hours while being worked (default 12h, configurable per client)

Today

Does not exist. Confirmed: zero scheduled-job library anywhere in the project (@nestjs/schedule, node-cron, node-schedule — all absent from package.json). No per-client settings surface exists to hang a configurable interval on (see V1).

Gap → V3

Two dependent pieces: (1) the Client entity from V1, carrying a notificationIntervalHours field defaulting to 12; (2) a scheduled job (@nestjs/schedule's @Cron is the smallest addition that fits this project's existing NestJS-native style) that finds in-progress trips whose client hasn't been emailed within their configured interval and sends one. Medium effort — this is genuinely new infrastructure, not a wiring exercise like V2. Sequence after V1.

DOnce complete, released for billing — may combine multiple services/trips for the same client into one invoice

Today

generateInvoiceFromTrip(tripId) takes exactly one trip ID (confirmed: BillingPage.tsx's "Generate Invoice" dialog picks a single trip from an eligible-trips list). No consolidation across trips exists in any form. "Released for billing" isn't a real state transition today — Trip.status is a free-text field with no enforced "Complete → ready to bill" workflow.

Gap → V4

Extend invoice generation to accept an array of trip IDs for one client, folding every confirmed service across all of them into one invoice's line items — the per-trip line-item logic already works and doesn't need to change, only its input shape and the UI that drives it (a client-scoped "select trips to bill together" view instead of one-trip-at-a-time). Depends on V1 for a reliable client grouping key. Medium effort, medium risk — touches billing, deserves its own careful pass and test coverage once built.

EAdmin maintains all reference data — clients, airports, countries, services, categories, tails/registrations, operators (clients may or may not be operators)

Today

Airports/Countries/Aircraft/Providers/Operators/Service Types/Country Rules/Leg Purposes are all already admin-manageable (Reference Data + Admin Assets, per this session's earlier work). Clients are the one missing piece — there is no client entity to maintain at all.

Gap

Fully covered by V1's Client model plus a Client CRUD tab in Reference Data or Admin Assets, following the exact same pattern already established for Operator/Provider. No new pattern to invent — this is the one piece of E that V1 doesn't just unblock, it directly is.
